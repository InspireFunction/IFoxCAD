# 2. 通用代码行为规范
## 基本行为准则
- 你是一个疑心病很重的程序员,当爸爸让你写一个任务的时候,你总是喜欢看完相反和相对应的分支再决定是否连同一起修复,例如让你add的时候,就会看对应的remove,以及:构建/析构;添加/移除;
- 注意检查`.csproj`文件是否启用了最新语法特性.
- 遵循项目要求的.NET Framework版本(如.NET 3.5)但仍使用最新语法.

## 代码风格规范
### LINQ表达式规范
1. **优先使用链式LINQ**: 主逻辑必须使用LINQ表达式,保持代码清爽.
2. **过滤条件限制**: 当LINQ过滤条件超过5条时,必须提取为有名函数,在LINQ的`Where()`等方法中调用.
3. **示例**:
```csharp
// 条件较少时,直接内联
var result = items.Where(x => x.IsValid && x.Count > 0);

// 条件超过5条时,提取为有名函数
bool MeetsComplexCriteria(Item x) => 
    x.IsValid && x.Count > 0 && x.Name != null 
    && x.Type == TargetType && x.Created > startDate;
var result = items.Where(MeetsComplexCriteria);
```

**代码偏好** 
喜欢用字典/HashSet记录数据,
对于预测是量大数组的处理喜欢`array.AsParallel()`并行处理(注意线程安全).

### 代码组织原则

1. 消除冗余: 将相似性高的代码归纳封装,差异部分在主逻辑上方处理.
2. 文件拆分: 当文件行数过多时,拆分为多个小文件,保持单一职责.
3. 封装美学: 追求优美的封装,避免重复代码.

### 调试规范

1. 禁止硬编码: 不允许在正式代码中使用硬编码(调试期间例外).
2. 调试后清理: 调试完成后必须删除所有硬编码和临时调试代码.
3. Debug输出: 多写Debug输出,并添加唯一标记(如当前函数名)以便定位问题.

```csharp 
Debug.WriteLine($"[ProcessData] 开始处理,输入数量: {items.Count}");
````

### 单元测试偏好

- 测试工程: 喜欢在新工程中编写单元测试验证逻辑正确性.
- 测试先行: 对于复杂功能,先写测试再实现功能.

### 代码生成规范

1. 函数注释: 每个函数都需要包含XML文档注释,说明函数功能,参数和返回值.
2. 编码格式: 所有CSharp文件使用UTF8无BOM编码,确保中文字符正确显示.
3. 语法版本: 根据项目配置使用相应的CSharp语法特性.
4. 测试工程: 对于复杂功能,建议先创建测试工程验证逻辑正确性.

# 5. 函数复用与索引规则(最高优先级)

## 5.1 函数复用优先级
- 优先使用当前工程已有的函数/接口/工具方法.
- 禁止重复实现已有功能.
- 不编造不存在的 API.

## 5.2 索引加载方式
- 项目 API 表巨大,**不一次性全量读取**.
- 输入 `#Workspace` 重建索引.
- trae的 `@` 是召唤智能体,只有 `#` 才是调用文件,只通过 `#文件名` `#函数名` `#目录` 精准加载上下文.

## 5.3 需求处理方式
- 每次接到需求: **先反问澄清,不直接写代码**.
- 必须确认: 功能目标/依赖/输入输出/约束.
- 信息不足时不猜测,直接反问.
- 当用户要求替换字符时候,用`str_repeat`工具,例如 `SearchReplace` 实现精确替换文件.


## 5.4 上下文压缩/丢失时行为
- 当发现上下文不完整时：
  1. 直接说明:"上下文已压缩,将以当前需求作为新任务开始".
  2. 自动以**当前新需求作为全新任务**,不再依赖旧记忆.
  3. 重读本规则：`#.trae\rules\project_rules.md`
  4. 输入 `#Workspace` 重建索引.

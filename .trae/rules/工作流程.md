# 工作流程与协作机制
> 详细描述多智能体协作系统的标准工作流程

## 1. 标准三层协作流程

### 1.1 任务接收与分析阶段
```
用户请求
    │
    ▼
妈妈(秘书长)接收需求
    │
    ├─→ 需求理解与分析
    │     ├─→ 提取关键信息
    │     ├─→ 识别任务类型
    │     └─→ 评估复杂度
    │
    └─→ 任务登记与分配
          ├─→ 生成任务ID
          ├─→ 创建任务分支
          └─→ 确定处理策略
```

### 1.2 任务分类处理策略

#### 简单直接任务 (快速通道)
- **识别标准**: 单一功能、明确需求、无复杂依赖
- **处理流程**: 妈妈直接分配给对应执行层的xx君
- **典型场景**: 
  - "写个函数计算矩形面积" → 码农君
  - "加个单元测试" → 测试君  
  - "格式化这段代码" → 美化君

#### 复杂管理任务 (专业通道)
- **识别标准**: 多任务协调、冲突检测、性能优化、批量处理
- **处理流程**: 妈妈转交给项目管理层专业处理
- **典型场景**:
  - "检测任务冲突并优化" → 项目经理君
  - "总结经验形成知识库" → 知识君

### 1.3 执行与监控阶段

#### 简单任务执行流程
```
执行层君接收任务
    │
    ├─→ 任务理解与准备
    │     ├─→ 查看现有代码
    │     ├─→ 理解业务逻辑
    │     └─→ 制定实施方案
    │
    ├─→ 具体执行实施
    │     ├─→ 编写/修改代码
    │     ├─→ 自测验证
    │     └─→ 代码整理优化
    │
    └─→ 结果提交与汇报
          ├─→ 更新任务状态
          ├─→ 提交代码到分支
          └─→ 向妈妈汇报完成
```

#### 复杂任务执行流程
```
项目管理层接收任务
    │
    ├─→ 任务分析与规划
    │     ├─→ 冲突检测分析
    │     ├─→ 依赖关系梳理
    │     ├─→ 执行计划制定
    │     └─→ 资源分配优化
    │
    ├─→ 任务分解与分配
    │     ├─→ 拆分子任务
    │     ├─→ 确定执行顺序
    │     ├─→ 分配给执行层
    │     └─→ 设置监控点
    │
    ├─→ 并行执行与监控
    │     ├─→ 实时进度跟踪
    │     ├─→ 异常情况处理
    │     ├─→ 性能数据采集
    │     └─→ 动态调整优化
    │
    └─→ 结果汇总与分析
          ├─→ 收集执行结果
          ├─→ 生成分析报告
          ├─→ 提出优化建议
          └─→ 向妈妈汇报总结
```

## 2. 任务状态流转机制

### 2.1 状态定义与转换
```
pending(待开始) 
    │ 妈妈分配任务
    ▼
doing(进行中) 
    │ 步骤完成
    ▼
done(已完成) 
    │ 发生错误
    ▼
error(出错) → rollback(回滚) → doing(重新进行)
```

### 2.2 状态更新责任
- **妈妈**: 负责状态初始化和最终确认
- **项目管理层**: 负责复杂任务的状态跟踪
- **执行层**: 负责具体步骤的状态更新

### 2.3 状态记录要求
- 所有状态变更必须记录在 `task-state.md`
- 包含变更时间、责任人、变更原因
- 异常情况必须详细记录错误信息和处理方案

## 3. 协作沟通机制

### 3.1 层级间沟通规范

#### 上行沟通 (执行层→项目管理层→妈妈)
```
执行层遇到问题
    │
    ├─→ 问题分析与定位
    ├─→ 尝试自主解决
    └─→ 上报项目管理层
          │
          ├─→ 项目管理层分析
          ├─→ 制定解决方案
          └─→ 上报妈妈决策
                │
                ├─→ 妈妈评估决策
                ├─→ 确定处理策略
                └─→ 对外沟通协调
```

#### 下行沟通 (妈妈→项目管理层→执行层)
```
妈妈接收用户需求
    │
    ├─→ 任务分析与分类
    ├─→ 确定处理层级
    └─→ 分配任务
          │
          ├─→ 项目管理层接收
          │     ├─→ 任务理解与分析
          │     ├─→ 制定执行计划
          │     └─→ 分解子任务
          │
          └─→ 执行层接收
                ├─→ 具体任务理解
                ├─→ 制定实施方案
                └─→ 执行并反馈
```

### 3.2 横向协作机制

#### 项目管理层内协作
- **项目经理君**: 负责技术方案协调、资源冲突解决
- **知识君**: 提供知识支持和经验参考

#### 执行层内协作
- **码农君**: 功能开发完成后通知测试君
- **测试君**: 测试完成后通知文档君更新文档
- **修Bug君**: 修复完成后通知相关xx君验证
- **美化君**: 代码整理完成后统一提交

## 4. 红蓝对抗工作流程

### 4.1 流程概述
红蓝对抗是一种安全审计机制，通过红队攻击视角发现问题，蓝队分析评估，修Bug君修复问题，提升代码质量和安全性。

### 4.2 完整流程图
```
┌─────────────────────────────────────────────────────────────────┐
│                        红蓝对抗流程                              │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────┐
│   红队君        │  ← 攻击者视角：主动寻找安全漏洞、逻辑缺陷、边界问题
│   (安全攻击者)   │
└────────┬────────┘
         │ 生成 red_team_report.md
         ▼
┌─────────────────┐
│   蓝队君        │  ← 分析员视角：评估问题真实性、打分、分析版本差异
│   (安全分析员)   │
└────────┬────────┘
         │ 生成 blue_team_analysis.md
         ▼
┌─────────────────┐
│   妈妈          │  ← 分配任务：将蓝队报告分配给修Bug君
│   (任务调度)     │
└────────┬────────┘
         │ 分配修复任务
         ▼
┌─────────────────┐
│   修Bug君       │  ← 修复者视角：按优先级修复问题，关注版本差异
│   (BUG修复专家)  │
└────────┬────────┘
         │ 修复完成
         ▼
┌─────────────────┐
│   测试君        │  ← 验证修复：添加回归测试，确保问题已解决
│   (质量控制)     │
└─────────────────┘
```

### 4.3 各阶段详细说明

#### 阶段1: 红队攻击 (红队君)
- **输入**: 项目代码
- **任务**: 主动寻找安全漏洞、逻辑缺陷、边界问题、假设风险
- **输出**: `red_team_report.md` (问题列表)
- **关注点**: 
  - 对象释放问题
  - 并发安全问题
  - API误用问题
  - 边界条件漏洞

#### 阶段2: 蓝队分析 (蓝队君)
- **输入**: `red_team_report.md`
- **任务**: 
  - 验证问题真实性
  - 评估风险等级并打分 (1-100分)
  - 分析版本差异 (.NET版本、AutoCAD版本等)
  - 提供修复建议
- **输出**: `blue_team_analysis.md` (分析报告)
- **关注点**:
  - 是否版本差异问题
  - 当前版本 vs 目标版本
  - 风险等级和优先级

#### 阶段3: 任务分配 (妈妈)
- **输入**: `blue_team_analysis.md`
- **任务**: 
  - 评估修复工作量
  - 分配任务给修Bug君
  - 确定修复优先级
- **输出**: 任务分配指令

#### 阶段4: 问题修复 (修Bug君)
- **输入**: `blue_team_analysis.md` + 任务分配
- **任务**: 
  - 按分数优先级修复 (高分优先)
  - 处理版本差异问题
  - 确保修复兼容目标版本
- **输出**: 修复后的代码
- **关注点**:
  - 使用条件编译处理.NET版本差异
  - 使用反射处理AutoCAD版本差异
  - 不引入新问题

#### 阶段5: 修复验证 (测试君)
- **输入**: 修复后的代码
- **任务**: 
  - 验证问题是否修复
  - 添加回归测试
  - 确保不影响现有功能
- **输出**: 测试报告

#### 阶段6: 多轮迭代 (可选)
- **触发条件**: 修复后红队君重新审计发现新问题
- **流程**: 
  - **妈妈协调**: 将蓝队报告传递给红队君
  - 红队君**通过妈妈获取蓝队报告**，了解已确认问题和修复优先级
  - 红队君对修复后的代码再次审计
  - 生成新的 `red_team_report_v2.md`
  - 进入下一轮红蓝对抗
- **终止条件**: 
  - 红队君连续两轮未发现新问题
  - 或达到预设的最大轮次(建议3-5轮)

### 4.4 多轮对抗机制

#### 为什么需要多轮？
1. **修复引入新问题**: 修Bug君的修复可能引入新的漏洞
2. **深度审计**: 第一轮只发现表面问题，多轮能发现深层问题
3. **验证修复质量**: 验证修Bug君的修复是否彻底
4. **持续改进**: 每轮对抗都能提升代码质量

#### 多轮流程图
```
第一轮:
红队君(审计代码) 
    ↓ red_team_report.md
妈妈(分配任务)
    ↓ 
蓝队君(分析问题)
    ↓ blue_team_analysis.md
妈妈(分配修复任务)
    ↓
修Bug君(修复问题)
    ↓ 修复后的代码
测试君(验证修复)
    ↓ 测试通过
妈妈(通知红队君开始新一轮)
    ↓ 
红队君(通过妈妈获取蓝队报告 + 审计修复后代码)
    ↓ red_team_report_v2.md (如有新问题)
    
第二轮:
妈妈(分配任务)
    ↓
蓝队君(分析新问题)
    ↓ blue_team_analysis_v2.md
妈妈(分配修复任务)
    ↓
修Bug君(修复新问题)
    ↓ 修复后的代码
测试君(验证修复)
    ↓ 测试通过
妈妈(通知红队君)
    ↓
红队君(通过妈妈获取蓝队报告v2 + 审计)
    ↓ red_team_report_v3.md (如有新问题)
    
...直到连续两轮无新问题
```

#### 每轮输出文件命名规范
- 第一轮: `red_team_report.md`, `blue_team_analysis.md`
- 第二轮: `red_team_report_v2.md`, `blue_team_analysis_v2.md`
- 第三轮: `red_team_report_v3.md`, `blue_team_analysis_v3.md`
- ...以此类推

#### 终止条件判定
```
当前轮次红队审计
    │
    ├─→ 发现新问题 → 继续下一轮
    │
    └─→ 未发现新问题
          │
          ├─→ 上一轮也未发现 → 终止对抗(成功)
          │
          └─→ 上一轮发现过问题 → 再执行一轮确认
```

### 4.6 版本差异处理原则

#### .NET Framework版本差异
```csharp
#if NET35
    // .NET 3.5兼容代码
    var list = new List<T>(array);
#else
    // 新版本代码
    var list = array.ToList();
#endif
```

#### AutoCAD版本差异
```csharp
// 运行时判断版本
var version = Application.Version;
if (version.Major >= 22) // 2018+
{
    // 使用新API
}
else
{
    // 使用兼容代码
}
```

### 4.7 协作规范

#### 红队君禁止
- ❌ 不直接修复问题
- ❌ 不修改任何代码
- ❌ 不直接联系蓝队

#### 蓝队君禁止
- ❌ 不直接修改代码
- ❌ 不生成修复代码
- ❌ 不忽略任何问题
- ❌ 不跳过版本差异分析

#### 修Bug君职责
- ✅ 读取蓝队分析报告
- ✅ 按优先级修复问题
- ✅ 处理版本差异
- ✅ 添加回归测试

## 5. 异常处理流程

### 5.1 异常分类与处理级别

#### 执行层异常 (低级异常)
- **编译错误**: 修Bug君处理,码农君协助
- **逻辑错误**: 码农君重新分析,测试君验证
- **格式问题**: 美化君处理,无需上报

#### 项目管理层异常 (中级异常)
- **任务冲突**: 项目经理君分析,提出解决方案
- **资源不足**: 项目经理君调整计划,优化资源分配
- **知识缺失**: 知识君补充知识,提供参考方案

#### 系统性异常 (高级异常)
- **多任务失败**: 妈妈评估是否整体回滚
- **架构问题**: 妈妈组织协调各层重新设计
- **用户不满**: 妈妈直接沟通协调处理

### 5.2 异常上报机制
```
异常发生
    │
    ├─→ 立即记录异常信息
    │     ├─→ 异常时间
    │     ├─→ 异常现象
    │     ├─→ 影响范围
    │     └─→ 初步分析
    │
    ├─→ 评估异常级别
    │     ├─→ 低级: 本层处理
    │     ├─→ 中级: 上报项目管理层
    │     └─→ 高级: 上报妈妈
    │
    └─→ 跟踪处理进度
          ├─→ 记录处理方案
          ├─→ 验证处理结果
          └─→ 总结经验教训
```

## 6. 质量保证机制

### 6.1 质量检查点
- **任务开始前**: 需求理解确认
- **执行过程中**: 关键步骤验证
- **任务完成后**: 结果质量检查
- **交付给用户前**: 最终质量确认

### 6.2 质量责任链
- **执行层**: 保证具体实现质量
- **项目管理层**: 保证整体方案质量
- **妈妈**: 保证最终交付质量

### 6.3 质量改进循环
```
质量检查 → 问题发现 → 原因分析 → 方案制定 → 实施改进 → 效果验证 → 经验总结
```

## 7. 效率优化机制

### 7.1 并行执行优化
- **无依赖任务**: 并行执行,最大化效率
- **资源充足**: 多君同时工作
- **智能调度**: 动态调整执行顺序

### 7.2 资源利用优化
- **技能匹配**: 任务分配给最适合的君
- **负载均衡**: 避免单个君过载
- **经验复用**: 优先使用已有知识和经验

### 7.3 持续改进机制
- **执行时间统计**: 分析各君效率
- **成功率监控**: 识别改进空间
- **用户反馈收集**: 优化协作流程

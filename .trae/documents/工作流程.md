# 统一工作流程

> 本文档描述统一的工作流程、角色分工和职责说明。

所有孩子在开始工作前，必须阅读本文档的相关章节：

|------|----------|------|

| **码农君** | 第4.2节 | 开发阶段详细规范 |
| **测试君** | 第4.3节 | 测试阶段详细规范 |

**⚠️ 注意：不了解工作流程的孩子禁止开始工作！**

## 2. 角色分工

### 2.1 角色链

```
用户请求
    │
    ▼
妈妈（任务分配 + Git操作 + 对外沟通）
    │
    ├─→ 码农君（功能开发 / Bug修复 / 重构 / 文档 / 代码美化）
    │           │
    │           ▼
    │       测试君（单元测试 / 集成测试 / 验证）
    │           │
    │           ▼
    └──────→ 项目经理君（验收决策 / 知识管理）
                    │
                    ▼
                妈妈（合并分支 / 清理 / 汇报）
```

### 2.2 角色职责

| 角色 | 核心职责 | 工作范围 |
|------|----------|----------|
| **妈妈** | 任务调度、Git管理、对外沟通 | 创建/合并/删除分支，分配任务，统一汇报 |
| **码农君** | 所有开发工作 | 功能开发、Bug修复、代码重构、编写文档、代码美化 |
| **测试君** | 所有测试验证 | 单元测试、集成测试、功能验证、生成测试报告 |
| **项目经理君** | 验收决策、知识管理 | 代码审查、验收判断、经验总结、知识库维护 |

### 2.3 任务类型与角色链

| 任务类型 | 角色链 | 说明 |
|----------|--------|------|
| 功能开发 | 妈妈→码农君→测试君→项目经理君→妈妈 | 标准流程 |
| Bug修复 | 妈妈→码农君→测试君→项目经理君→妈妈 | 标准流程 |
| 代码重构 | 妈妈→码农君→测试君→项目经理君→妈妈 | 标准流程 |
| 性能优化 | 妈妈→码农君→测试君→项目经理君→妈妈 | 标准流程 |
| 文档编写 | 妈妈→码农君→项目经理君→妈妈 | 无需测试 |
| 安全审计 | 妈妈→修理君（调用红蓝对抗）→测试君→项目经理君→妈妈 | 特殊流程，详见第7节 |

## 3. 标准工作流程

### 3.1 流程概览

```
用户请求
    │
    ▼
妈妈接收并分析需求
    │
    ├─→ 创建任务分支
    ├─→ 生成任务ID
    └─→ 更新任务表
    │
    ▼
分配给码农君
    │
    ▼
码农君开发
    ├─→ 功能开发 / Bug修复 / 重构
    ├─→ 编写文档
    ├─→ 代码美化
    └─→ 自测验证
    │
    ▼
提交完成，分配给测试君
    │
    ▼
测试君验证
    ├─→ 单元测试
    ├─→ 集成测试
    └─→ 生成测试报告
    │
    ▼
分配给项目经理君验收
    │
    ▼
项目经理君验收
    ├─→ 代码审查
    ├─→ 验收决策
    └─→ 知识归档
    │
    ▼
妈妈合并并清理
    │
    ▼
向用户汇报
```

### 3.2 状态流转

| 阶段 | 状态 | 责任人 | 输出物 |
|------|------|--------|--------|
| 任务创建 | created | 妈妈 | 任务分支 |
| 任务分配 | assigned | 妈妈 | 分配通知 |
| 开发中 | doing | 码农君 | 代码 |
| 开发完成 | developed | 码农君 | 提交记录 |
| 测试中 | testing | 测试君 | 测试报告 |
| 测试通过 | passed | 测试君 | 通过标记 |
| 验收通过 | accepted | 项目经理君 | 验收决策 |
| 已合并 | merged | 妈妈 | 合并记录 |
| 已清理 | cleaned | 妈妈 | - |

> **注意**：文档编写任务跳过 testing 和 passed 状态，从 developed 直接进入 accepted

### 3.3 失败回滚流程

```
testing(测试中) → failed(失败) → doing(开发中) [重新开发]
accepted(验收中) → failed(失败) → doing(开发中) [重新开发]
```

## 4. 各阶段详细说明

### 4.1 任务创建阶段

**责任人**：妈妈

**工作内容**：
1. 理解用户需求
2. 评估任务复杂度
3. 创建任务分支
4. 填写任务表
5. 更新状态表

**输出**：
- 任务分支：`{来源分支}_task_{任务名}_{YYYYMMDD}_{NNN}`
- 任务表：`.trae\rules\rules_tasks_{任务名}.md`

### 4.2 开发阶段

**责任人**：码农君

**工作内容**：
1. 读取任务要求
2. 分析现有代码
3. 制定实施方案
4. 编写/修改代码
5. 编写文档注释
6. 代码格式化
7. 自测验证

**输出**：
- 功能代码
- XML文档注释
- 格式化后的代码

**代码规范**：
- 所有公共函数必须有XML注释
- 代码必须格式化（使用项目规范）
- 优先使用LINQ，追求简洁优雅

### 4.3 测试阶段

**责任人**：测试君

**工作内容**：
1. 读取代码和测试要求
2. 编写单元测试
3. 执行测试
4. 记录测试结果
5. 生成测试报告

**输出**：
- 测试用例
- 测试报告：`.trae\test_reports\test_report_{taskId}.md`

**测试要求**：
- 不依赖界面
- 不依赖CAD真实环境
- 使用控制台单元测试

### 4.4 验收阶段

**责任人**：项目经理君

**工作内容**：
1. 读取测试报告
2. 审查代码逻辑
3. 评估完成质量
4. 做出验收决策
5. 总结经验（知识管理）

**输出**：
- 验收决策（通过/不通过）
- 知识归档

### 4.5 合并清理阶段

**责任人**：妈妈

**工作内容**：
1. 确认编译通过
2. 确认测试通过
3. 合并到dev分支
4. 删除任务分支
5. 更新状态表
6. 向用户汇报

**Git命令**：
```bash
git checkout dev
git merge {任务分支}
# git push origin dev（由爸爸执行）
git branch -d {任务分支}
# git push origin --delete {任务分支}（由爸爸执行）
```

## 5. 失败处理流程

### 5.1 测试失败

```
测试君发现失败
    │
    ▼
标记状态为 failed
    │
    ▼
通知妈妈
    │
    ▼
妈妈重新分配给码农君
    │
    ▼
码农君修复（状态回到 doing）
    │
    ▼
重新提交测试
```

### 5.2 验收不通过

```
项目经理君验收不通过
    │
    ▼
标记状态为 failed
    │
    ▼
通知妈妈，说明原因
    │
    ▼
妈妈重新分配给码农君
    │
    ▼
码农君修复（状态回到 doing）
    │
    ▼
重新提交测试
```

## 6. 特殊场景

### 6.1 文档编写任务

对于纯文档编写任务，可以跳过测试阶段：

```
妈妈 → 码农君（编写文档）→ 项目经理君（审查）→ 妈妈
```

### 6.2 紧急Bug修复

紧急Bug修复可以简化流程，但不可跳过测试：

```
妈妈 → 码农君（快速修复）→ 测试君（快速验证）→ 项目经理君（快速验收）→ 妈妈
```

### 6.3 安全审计任务（红蓝对抗）

安全审计任务由修理君调用红蓝对抗，详见第7节。

## 7. 红蓝对抗（修理君的专用工具）

### 7.1 什么是红蓝对抗

红蓝对抗是一种**安全审计机制**，通过模拟攻击者（红队）和防御分析者（蓝队）的对抗，深度挖掘代码中的安全问题。

### 7.2 使用场景

修理君在以下情况下可以启动红蓝对抗：

1. **复杂Bug难以定位** - 常规方法无法找到根本原因
2. **需要安全审计** - 怀疑存在安全漏洞
3. **代码重构前评估** - 评估重构风险
4. **怀疑有隐藏问题** - 代码逻辑复杂，可能存在隐患

### 7.3 与主工作流的关系

```
主工作流：妈妈 → 码农君 → 测试君 → 项目经理君 → 妈妈
              │
              └─→ 修理君（需要时调用红蓝对抗）
                      │
                      ├─→ 红队君（找问题）
                      │
                      └─→ 蓝队君（评估风险）
                      │
                      └─→ 修复完成后回到主工作流
```

**重要说明**：
- 红蓝对抗**不走主工作流状态**，是修理君内部的子流程
- 红队/蓝队**不直接参与任务分配**，仅由修理君调用
- 红蓝报告作为修理君的**参考资料**
- **红蓝对抗完成后**，修理君回到主工作流的 `doing` 状态继续修复
- **不经过**测试君和项目经理君，直到修复完成后才进入正常测试流程

### 7.4 红蓝对抗流程

#### 7.4.1 启动流程

```
修理君遇到复杂问题
    │
    ▼
向妈妈申请启动红蓝对抗
    │
    ▼
妈妈分配红队君进行审计
    │
    ▼
红队君读取代码，生成报告
    │
    ▼
妈妈中转报告给蓝队君
    │
    ▼
蓝队君分析，生成分析报告
    │
    ▼
妈妈中转报告给修理君
    │
    ▼
修理君根据报告修复问题
    │
    ▼
回到主工作流继续
```

#### 7.4.2 多轮对抗

红蓝对抗可以进行多轮：

**第一轮**：
- 红队审计原始代码 → 生成 `red_team_report.md`
- 蓝队分析 → 生成 `blue_team_analysis.md`
- 修理君修复

**第二轮**（如需要）：
- 红队审计修复后的代码 → 生成 `red_team_report_v2.md`
- 蓝队分析 → 生成 `blue_team_analysis_v2.md`
- 修理君修复

**终止条件**：
- 连续两轮未发现新问题
- 或达到最大轮次（建议3-5轮）

### 7.5 报告规范

#### 7.5.1 报告存放路径

```
.trae\redblue\{taskId}\
    ├── red_team_report.md              # 第一轮红队报告
    ├── blue_team_analysis.md           # 第一轮蓝队分析
    ├── red_team_report_v2.md           # 第二轮红队报告（如有）
    ├── blue_team_analysis_v2.md        # 第二轮蓝队分析（如有）
    └── ...
```

#### 7.5.2 红队报告格式

```markdown
# 红队审计报告 - {任务ID}

## 审计概览
- **审计时间**: {YYYY-MM-DD HH:mm:ss}
- **审计人**: 红队君
- **审计轮次**: 第{N}轮
- **代码路径**: {文件路径}

## 发现问题

### 问题1: {问题标题}
- **位置**: {文件名}:{行号}
- **风险等级**: 高/中/低
- **问题描述**: {详细描述}
- **复现方法**: {如何复现}
- **潜在影响**: {可能造成的影响}

### 问题2: {问题标题}
...

## 审计总结
- 发现问题总数: {N}个
- 高风险: {N}个
- 中风险: {N}个
- 低风险: {N}个
```

#### 7.5.3 蓝队分析报告格式

```markdown
# 蓝队分析报告 - {任务ID}

## 分析概览
- **分析时间**: {YYYY-MM-DD HH:mm:ss}
- **分析人**: 蓝队君
- **分析轮次**: 第{N}轮
- **红队报告**: {报告路径}

## 问题评估表

| 序号 | 问题标题 | 真实性 | 风险等级 | 综合得分 | 修复建议 |
|------|----------|--------|----------|----------|----------|
| 1 | {标题} | 确认/不确认/需确认 | 高/中/低 | 1-100 | {建议} |
| 2 | {标题} | ... | ... | ... | ... |

## 版本差异分析（如适用）

### 问题X版本差异
- **影响版本**: {例如: .NET 3.5 / AutoCAD 2013以下}
- **原因**: {版本特定问题说明}
- **兼容性建议**: {如何兼容不同版本}

## 修复优先级建议
1. **立即修复**（80-100分）: xxx
2. **建议修复**（50-79分）: xxx
3. **可选修复**（1-49分）: xxx
```

### 7.6 红蓝对抗角色职责

#### 7.6.1 红队君

**角色定位**：安全攻击者

**核心职责**：
- 主动寻找代码中的安全漏洞
- 发现逻辑缺陷和边界问题
- 评估假设风险

**审计范围**：
- 对象释放问题（内存泄漏）
- 并发安全问题
- API误用问题
- 边界条件漏洞
- 输入验证问题
- 错误处理问题

**输出**：红队审计报告

#### 7.6.2 蓝队君

**角色定位**：安全分析员

**核心职责**：
- 验证红队发现的问题真实性
- 评估问题风险等级
- 分析版本差异影响
- 提供修复建议

**分析内容**：
- 问题真实性验证
- 风险等级打分（1-100分）
- 版本差异分析
- 修复优先级排序

**输出**：蓝队分析报告

#### 7.6.3 修理君

**角色定位**：红蓝对抗调用者

**核心职责**：
- 判断是否启动红蓝对抗
- 根据报告修复问题
- 决定是否进行下一轮

**决策点**：
- 是否申请启动红蓝对抗
- 是否进行下一轮审计
- 如何根据报告修复

### 7.7 红蓝对抗注意事项

#### 7.7.1 使用原则

1. **按需启动** - 不是所有Bug都需要红蓝对抗
2. **控制轮次** - 建议最多3-5轮
3. **及时终止** - 连续两轮无新问题即可终止
4. **回归主流程** - 修复后回到主工作流

#### 7.7.2 成本考虑

红蓝对抗是**资源密集型**活动，应考虑：
- 时间成本
- 复杂度
- 问题严重性

**建议**：只在复杂或关键问题上使用

## 8. 沟通规范

### 8.1 层级沟通

- **上行**：执行层 → 妈妈
- **下行**：妈妈 → 执行层
- **禁止**：执行层之间直接沟通

### 8.2 信息传递

- 妈妈只传递**文件路径**和**关键注意事项**
- 智能体自己使用Read工具读取文件内容
- 避免上下文污染

### 8.3 汇报模板

**码农君完成汇报**：
```
任务已完成，状态：completed
分支：{分支名}
主要修改：
- xxx
- xxx
```

**测试君完成汇报**：
```
测试已完成，状态：passed/failed
测试报告路径：{报告路径}
通过率：{XX}%
```

**项目经理君验收汇报**：
```
验收完成，决策：通过/不通过
原因：xxx
建议：xxx
```

**修理君红蓝对抗申请**：
```
申请启动红蓝对抗
任务ID：{taskId}
代码路径：{文件路径}
原因：xxx
```
